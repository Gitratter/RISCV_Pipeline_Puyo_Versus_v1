# RISC-V ぷよぷよ風ゲーム：２人対戦のルールと検証

## 1. 処理主体と既存版の継承

本版は、ゲーム判定を専用 Verilog 回路へ戻す実装ではない。既存の RV32I パイプライン CPU が C で記述されたゲームと対戦管理を実行する。`game.c` は共通の一人分の処理、`match.c` は二人分の状態・相殺・勝敗・開始を管理する。P1/P2 は同じ処理関数を使い、独立した `PuyoGame` を保持する。

ハードウェアは CPU、同期 BRAM、入力同期・デバウンス、キーボード受信、時計、MMIO 表示データ保持、VGA 走査を担当する。表示用盤面のレジスタは CPU の状態を受け取るコピーであり、衝突・探索・相殺の正本ではない。二人の交互操作ではなく、CPU が両者を継続的に更新する。片方が連鎖・おじゃま落下中でも、もう片方の状態を同じ更新で処理する。

既存の通常四色、移動・回転、簡易着地、落下、スコア式、NEXT、乱数の再戦時継続を基盤としている。１人用の PLAY 画面は既存 `PuyoVideo.v` を維持し、開始・終了案内と対戦画面を追加した。詳細な配置は `VIDEO.md`、キーボードと接続の根拠は `KEYBOARD.md` を参照。

## 2. 盤面・共通操作

内部盤面は横6×縦14。`board[y*6+x]` とし、`x=0..5`、`y=0..13`。上側の二行 `y=0,1` は出現・回転用の非表示領域で、固定後の落下・消去判定には含める。可視盤面は横6×縦12である。

セル値は 0=空、1..4=通常四色、5=おじゃま。操作中の二個は固定盤面と別管理し、軸 `(2,1)`、子 `(2,0)`、向き上で出現する。向き 0/1/2/3 は上/右/下/左。回転先と移動先の二個を範囲・占有チェックし、失敗した操作は位置・向きを変更しない。壁蹴り・クイックターン・着地猶予はない。

| 項目 | 共通の通常設定 |
|---|---:|
| 自動落下 | 700 ms / マス |
| 高速落下 | 40 ms / マス |
| 左右長押しの初回待ち | 180 ms |
| 左右長押しの反復間隔 | 60 ms |
| 固定後の一段落下表示 | 40 ms |
| 消去対象の表示時間 | 180 ms |

左右は押下時に一マス、長押し後に反復。左右同時押しでは移動しない。回転は新しい押下時だけ実行し、左右回転同時押しは無効。P2 のキーボードから同一 make code が繰り返されても、新しい押下として回転しない。左右移動と回転、左右移動と高速落下は組み合わせて使える。

P1 はボードの L/R/D、U=右回転、C=左回転を維持する。P2 は ←/→/↓、Z=左回転、X=右回転。SW0 は開始時のモード選択、SW14 の 0→1 は開始・再戦用で、対戦 PLAY 中は無効。１人用 PLAY 中は既存の使い方に合わせ SW14 再開始を許可する。SW15 はゲーム操作から分離されたシステムリセットである。

## 3. 同じ出現順と再戦時の乱数

試合開始時に、両者の通常ぷよ RNG に同じ seed を設定する。以後はそれぞれが NEXT を生成するときだけ自分の RNG を進める。共有 RNG を早い者順で消費しないため、プレイ速度が異なっても P1 の n 組目と P2 の n 組目が一致する。同色二個の組も出現する。

おじゃまの余り列抽選は `garbage_rng` を使い、通常の `rng` を変更しない。両プレイヤーの `garbage_rng` は試合 seed から別々に初期化する。おじゃま数・抽選回数が異なっても通常ぷよの順番に影響しない。

通常の再戦ではセッション RNG を保持して進め、ミリ秒時刻を混ぜる。毎回同じ固定 seed へ戻す旧問題は再導入していない。疑似乱数なので同じ色や組が偶然出ることは正常であり、電源投入・全体リセット後まで常に異なることを保証する真性乱数ではない。試験では `match_start` に明示的な seed を渡せる。共通ゲーム API の固定 `PuyoPair` 列も引き続き使用できる。

## 4. 消去・重力・攻撃量

固定後は「全盤面の落下 → 全盤面の連結探索 → 全対象の同時消去 → 再落下」を繰り返す。列内の上下順序を保持し、空きがなくなってから探索する。横向きの組が段差へ固定されれば、支えのない側だけが落ちる。

通常色の上下左右の連結成分を有限長の幅優先探索で調べ、4個以上ならすべて消去対象とする。斜めは接続しない。全盤面のマーキング後に消去するため、離れた成分の同時消去は一段階であり、二連鎖とは数えない。探索キューは最大84セル、再帰・heap は使用しない。

おじゃまは単独でも集団でも同色成分として探索しない。通常ぷよの消去マークが確定してから、直接上下左右に接するおじゃまだけに消去マークを付ける。おじゃまのマークを起点に伝播しない。共有して隣接する一個は一回だけ消去する。おじゃま数は通常消去数・スコア・攻撃量に加えず、おじゃまだけで連鎖を増加させない。

表示スコアは既存の「通常消去数×10×連鎖数」。攻撃は独立して、各消去段階について次式を加算する。

`段階攻撃量 = floor(通常消去数 / 4) × 連鎖係数`

| 連鎖段階 | 1 | 2 | 3 | 4 | 5 | 6 | 7以降 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 係数 | 1 | 2 | 4 | 8 | 12 | 18 | 18 |

係数は `game_attack_factor` の定数表で調整できる。4個消しは1、4個ずつの二連鎖は3、三連鎖は7となる。二か所で4個ずつ同時消去した場合は通常消去数8による攻撃2である。連鎖途中では送信せず、その組の全連鎖終了まで `round_attack` に蓄積する。

## 5. 論理更新と公平な相殺

ここでの「同時」は FPGA の同一物理クロックではなく、**同じ時刻スナップショットを使う一回の `match_step` 論理更新**である。同じミリ秒値で関数を再呼出ししても状態更新を繰り返さない。実行が遅れた場合は次に取得した時刻で更新し、過去の時刻を多数まとめて再生しない。CPU 内では命令を順番に実行するが、各プレイヤーを一段階ずつ進めた後に、両者の確定イベントをまとめて判定する。

各プレイヤーは連鎖が終わると `GAME_BOUNDARY` と `turn_ready=1` で待つ。この通知は中央管理が消費するまで保持される。相殺・予約後に `game_finish_turn` が通知をクリアするため、複数回読み取って同じ攻撃を重複加算しない。

一回の中央処理は次の順序である。

1. 両者のプレイヤー処理を進め、敗北確定があれば結果へ移る。
2. 両者の確定攻撃と更新前の予告数を取得する。
3. 各自の攻撃で各自の旧予告を相殺する。
4. 残った送信攻撃同士を相殺する。
5. 差分だけを相手の予告に加える。
6. 今回境界通知を出したプレイヤーについて、更新後予告から降下数を予約する。

予告10への攻撃6なら予告4・送信0、攻撃14なら予告0・送信4。両予告0で攻撃10対6が同時確定すれば、P2の予告に4だけ加える。P1から順に相手の予告を直接変更する手順ではないため、処理番号による先手有利を避ける。

### カウンタの上限

予告は16 bit unsigned、上限65535で飽和する。更新の中間計算は32 bitで行い、加算による巻戻りと減算の負数化を防ぐ。上限を超えた分は当該更新の `clipped[]` および受信側の `overflow_total[]` に記録する。これは無制限の保存ではなく、**65535を超える予告は保持せず超過量を記録する簡略仕様**である。

`attack_total`、`sent_total`、`received_total`、`cancelled_total`、`drop_total`、`overflow_total` は32 bit飽和の診断用累計で、再戦時にクリアする。`cancelled_total` は自分の旧予告を減らした数で、送信攻撃同士の相殺数ではない。`overflow_total` は予告カウンタ上限の超過量であり、盤面のあふれによる敗北フラグ `garbage_overflow` とは異なる。

## 6. 降下予約・配置・途中受信

自分の組の全連鎖が終わり、相殺と受信が終わってから、一回だけ `min(予告,30)` を予約する。予約分は直ちに `pending` から除かれ、その後は相殺対象ではない。31なら今回30、残り1は予告のまま残し、次の操作組を経て次回の境界で扱う。操作の機会なしに30ずつ繰り返さない。

降下開始時の列配分は、全六列へ `予約数 / 6` 個ずつ、余りを重複しない列へ一個ずつ加える。余り列は部分 Fisher–Yates 抽選で選ぶ。8個なら六列に一個、さらに異なる二列に一個。列は予約時点で決まり、空きの多い列へ振り替えない。

`garbage_columns[x]` はその列へまだ挿入していない予約数、`garbage_inflight` は全列の**未挿入残数**である。この値は予約直後には予約数と等しく、内部上端セルへ挿入するたびに一つ減る。すでに挿入して落下中のものは `board` に含まれる。したがって `garbage_inflight=0` だけでは着地完了を意味しない。未挿入予約と盤面に挿入済みの落下中ぷよの両方が、予告から分離された非相殺対象である。

各列の内部最上段 `y=0` だけに挿入し、一波が安定してから次の波を挿入する。途中の空洞へ直接書き込まず、既存セルを上書きしない。上端が埋まっていれば `garbage_overflow` を立て、他の列へ振り替えない。その波で配置できたぷよの落下が完了した後に敗北を確定する。敗北によって処理を止めた場合は、未挿入の予約が残り得る。

`drop_total` は着地済み数ではなく、予約した数の累計である。降下処理中に追加攻撃を受けた分は `pending` に入り、進行中の予約を増やさない。通常状態では「予告」「未挿入予約」「盤面への挿入済み」を分けて数を追跡する。予告飽和時の超過と、敗北時に残る未挿入予約は別途区別する。

降下後は通常色の再探索を行わず、次の出現へ進む。ここで追加するのは無色のおじゃまのみであり、連鎖終了後の安定盤面に上から積むため、通常色の相互配置を変更して新たな色連結を作らない。

## 7. 勝敗・開始・再戦

通常の敗北は、全処理後の次の出現二マスが埋まっている場合。おじゃまを内部上端に配置できない場合も敗北である。同じ `match_step` で両者の敗北が確定したら DRAW、異なる更新なら先に確定した方が負けとなる。

通常出現判定は `GAME_SPAWN` のプレイヤー処理に置く。相殺の後でP1だけ即座に出現判定するような追加経路を作らない。これにより通常出現失敗とおじゃまあふれという異なる要因でも、同じ論理更新で確定した敗北は DRAW と扱える。

結果確定後は両者のゲーム更新、相殺、新規攻撃、新規降下を停止する。表示回路と時計は動作を続け、結果を表示する。再戦では新しい seed を使い、両盤面、探索配列、組、NEXT、スコア、連鎖、予告、予約、累計、タイマーを初期化する。

開始前は通常3秒のカウントダウンを設ける。両者の落下タイマーは PLAY 開始時刻に揃える。開始時に押されている操作キーは個別にブロックし、そのキーが解放されるまで受け付けない。保持キーの再送を新しい回転として扱わない。開始スイッチ自身も立上りのみであり、保持中に再戦を繰り返さない。

## 8. 原作との主な違い

- 攻撃量は本仕様の独自係数。原作の得点換算・色数・全消しボーナスなどは実装しない。
- 連鎖終了時に一括相殺・送信し、連鎖途中の逐次送信は行わない。
- 一組につき一度、最大30個を降らせ、残りは次の組へ持ち越す。
- 上二行を含めて落下・連結探索を行い、出現二マスの閉塞を終了条件とする。
- 壁蹴り、クイックターン、着地猶予、特殊な組、時間経過による攻撃倍率はない。
- おじゃまの落下は列単位に割当てた波を順に安定させる簡易アニメーション。
- 同時性は物理クロック一致ではなく、共有時刻によるCPU上の論理更新単位。
- 予告は65535で飽和し、超過を記録する。

## 9. 検証結果と範囲

本版の検証結果は次のように区別する。

| 検証段階 | 結果 | 確認できる範囲 |
|---|---|---|
| ホスト上の同じC | 既存26/26、対戦32/32 PASS | ルール・状態更新・相殺など。ネイティブコンパイル/実行とも正常終了 |
| 自作RV32I CPU上のC | 既存26/26、対戦32/32 PASS | 実命令、同期メモリを経由した同じルール試験 |
| RTLシミュレーション | 22ベンチの実行・アサーション PASS | CPU回帰、入力、MMIO、VGA、統合等。ただし下記コンパイラ制限あり |
| Vivado合成・配置配線 | 完了、25 MHz制約達成、DRC 0 | 対象FPGAへの配置可能性と静的タイミング |
| Basys 3実機 | 未確認 | 実キーボード互換性、モニタ表示、実プレイは未検証 |

対戦32ケースの番号と内容は `tests/README_VERSUS.md`。既存26ケースは `tests/README.md`。対戦試験でも実装とは別の代替ゲームモデルを使わず、同じ `game.c` と `match.c` をホストとRV32Iで実行する。

### シミュレータ終了の制限

今回のWindows Icarus環境では、22ベンチすべてのコンパイルでコード生成の `DONE` 後にアクセス違反終了コード `3221225477` が発生した。したがって **コンパイラの正常終了は0/22** であり、「22本のコンパイルが正常完了した」とは報告しない。

新規生成された出力を確認したうえでVVPに渡し、22ベンチの実行・アサーションはPASSとなった。古い生成物を再利用した結果ではない。コード生成後の異常終了は未解決であり、機能検証の成功とコンパイラ異常は分けて記録する。XSimについてはVERIFICATION.mdを参照。xvlog解析は成功したがxelabの生成Cコンパイルに失敗しており、完走成功とはしていない。

### FPGA実装

対象はBasys 3、`xc7a35tcpg236-1`、Vivado 2025.2。入力100 MHzをMMCMで25 MHzへ変換し、CPU・周辺回路・VGAを動作させる。次は本版の配置配線後の結果であり、以前の一人用の値ではない。

| 指標 | 結果 |
|---|---:|
| Slice LUT | 5241 |
| Slice Register | 4295 |
| RAMB36 | 5 |
| DSP | 0 |
| WNS | +8.576 ns |
| TNS | 0 ns |
| WHS | +0.025 ns |
| DRC違反 | 0 |

25 MHzの指定制約を満たしたことと、実機プレイ確認は別である。WNSから単純換算した値を実機保証Fmaxとはしない。実機未確認のため、一般のUSBキーボードすべての互換性、画面の見え方、操作遅延・最悪処理時間は最終評価を保留する。
